## Завдання 1. Діагностика через EXPLAIN ANALYZE

Повний вивід — [results/explain_before.txt](results/explain_before.txt). Ключовий вузол:

```
->  Parallel Seq Scan on bookings  (cost=0.00..86606.68 rows=237043 width=10)
                                   (actual time=0.030..170.257 rows=184889 loops=3)
      Filter: ((created_at >= '2026-01-01 00:00:00+00') AND (status = 'paid'))
      Rows Removed by Filter: 1481777
      Buffers: ...
 Buffers: shared hit=13086 read=42286
 Execution Time: 220.367 ms
```

- **Seq Scan** один: `Parallel Seq Scan on bookings`, його виконують 3 процеси (лідер + 2 воркери, `loops=3`).
- **Планова кількість рядків** — `rows=237043` (оцінка на один процес; для паралельного плану PostgreSQL ділить загальну оцінку ≈ 569 тис. на 2,4). **Фактична** — `actual rows=184889` на кожен із 3 процесів, тобто 554 668 загалом. Оцінка планувальника близька до реальності.
- **Час:** вузол сканування — `actual time=0.030..170.257` мс (час на один процес). **Execution Time** усього запиту — **220,4 мс**.
- Кожен процес відкинув фільтром 1 481 777 рядків, разом ≈ 4,45 млн. Тобто 89 % прочитаної роботи викидається.

**Чому повний скан дорогий.** Таблиця займає **55 355 сторінок** по 8 КБ (`pg_class.relpages`), це **432 МБ**. Seq Scan не знає, на яких сторінках лежать потрібні рядки, тому читає **всі** сторінки: `shared hit=13086 + read=42286 = 55 372` буферів (сторінки таблиці + службові). На кожній сторінці ~90 рядків, і для кожного перевіряється умова. Обсяг роботи залежить від розміру таблиці (кількості сторінок), а не від кількості потрібних рядків.

**Чому в нас 220 мс, а не 20–25 с, як у легенді.** Вся таблиця (432 МБ) вміщується в оперативну пам'ять машини, тому `read=42286` фактично читаються з кешу ОС, а не з диска. Крім того, працюють 2 паралельні воркери. На сервері з повільним диском і холодним кешем ті самі 55 тис. сторінок читалися б з диска, і час зростав би в десятки разів. Суть від цього не змінюється: запит читає всю таблицю заради 11 % рядків.

> Примітка про одиниці: `cost=0.00..86606.68` — це умовні одиниці планувальника (вартість читання сторінки = 1), а **не** мілісекунди. Мілісекунди — лише в `actual time` і `Execution Time`.

## Завдання 2. Проєктування та додавання індексу

### Крок 1: композитний індекс

```sql
CREATE INDEX idx_bookings_status_created ON bookings (status, created_at);
```

**Чому B-Tree, а не Hash.** Умова має дві частини: `status = 'paid'` — рівність, `created_at >= '2026-01-01'` — **діапазон**. Hash-індекс уміє лише рівність і не підтримує `>=`, `<`, `BETWEEN` чи впорядкування, тому для діапазону дат він марний. Крім того, Hash не буває композитним. B-Tree зберігає ключі відсортованими, тому шукає і рівність, і діапазон.

**Чому порядок `(status, created_at)`, а не навпаки.** У B-Tree записи відсортовані спочатку за першим стовпцем, потім за другим. Для `(status, created_at)` усі записи з `status = 'paid'` лежать поруч, а всередині них — за датою. Пошук стає одним суцільним відрізком: «знайти `paid`, 2026-01-01 → читати до кінця `paid`». Для `(created_at, status)` діапазон за датою охопив би всі чотири статуси впереміш, і `status` довелося б фільтрувати всередині діапазону, тобто читати в 4 рази більше записів індексу. Правило: **стовпці з рівністю — першими, стовпець з діапазоном — останнім**.

### Крок 2: покривний індекс

Після кроку 1 запит став **повільнішим** (див. Завдання 3). Тому індекс замінено на покривний:

```sql
CREATE INDEX idx_bookings_paid_report
    ON bookings (status, created_at) INCLUDE (hotel_id, total);
VACUUM ANALYZE bookings;
```

`INCLUDE (hotel_id, total)` додає в листки індексу ще два стовпці, потрібні для `GROUP BY` і `SUM`. Тепер запит отримує всі дані з індексу і не ходить у таблицю. `VACUUM` оновлює visibility map: без неї PostgreSQL не впевнений, що рядок видимий, і все одно перевіряє таблицю.

### Вартість INSERT

Вимір — [sql/05_insert_cost.sql](sql/05_insert_cost.sql), вивід — [results/insert_cost.txt](results/insert_cost.txt). Вставка 200 000 рядків у транзакції з `ROLLBACK`:

| | Час |
|---|---|
| з покривним індексом | 1091 мс |
| без додаткового індексу | 526 мс |

Кожен `INSERT` тепер оновлює не лише таблицю й первинний ключ, а й ще один B-Tree (вставка в потрібне місце, іноді розщеплення сторінки). Масова вставка стала приблизно **у 2 рази повільнішою**, а індекс займає **259 МБ** на диску.

**Чи виправданий компроміс для `bookings`.** Так. Бронювання додаються по одному, і зайві кілька мікросекунд на рядок клієнт не помітить. Звіт фінансового відділу виконується регулярно і без індексу щоразу читає всю таблицю. Якщо таблиця зростатиме, а звіт залишиться щотижневим, альтернативою може бути матеріалізоване представлення, що оновлюється раз на тиждень.

## Завдання 3. Повторний вимір і кількісна оцінка

| Варіант | Вузол сканування | Execution Time | Прискорення |
|---|---|---|---|
| без індексу | Parallel Seq Scan | 220,4 мс | — |
| `(status, created_at)` | Parallel **Bitmap Heap Scan** + Bitmap Index Scan | 309,7 мс | ×0,71 (повільніше) |
| `(status, created_at) INCLUDE (hotel_id, total)` | Parallel **Index Only Scan**, `Heap Fetches: 0` | **112,2 мс** | **×1,96** |

Повні плани: [results/explain_after_index1.txt](results/explain_after_index1.txt), [results/explain_after_index2.txt](results/explain_after_index2.txt).

**Чому з'явився саме Bitmap Heap Scan.** Умова вибирає 11 % таблиці. Для такої вибірковості звичайний Index Scan стрибав би по таблиці в довільному порядку, по одній сторінці на кожен із 554 тис. рядків. Тому планувальник обирає Bitmap: спочатку з індексу будує бітову карту потрібних сторінок (`Bitmap Index Scan`, 2 129 сторінок індексу), потім читає ці сторінки таблиці **по порядку** (`Bitmap Heap Scan`). Index Scan вибирається, коли рядків дуже мало (частки відсотка). Seq Scan — коли потрібна більша частина таблиці.

**Чому крок 1 не прискорив, а сповільнив запит.** Дати й статуси розподілені рівномірно, тож потрібні 11 % рядків розкидані по **всіх** сторінках: на кожній сторінці з ~90 рядків приблизно 10 підходять. Bitmap Heap Scan усе одно прочитав майже всю таблицю (`Buffers: read=57483` ≈ 55 355 сторінок таблиці + 2 129 сторінок індексу), а ще витратив час на читання індексу і побудову бітової карти. Крім того, Bitmap Heap Scan читає сторінки вибірково, а не одним суцільним потоком, як Seq Scan. Індекс допомагає, коли зменшує кількість **сторінок**, а не лише рядків.

**Чому покривний індекс дав лише ×2, а не ×100.** Index Only Scan читає лише індекс (`Heap Fetches: 0`), і йому не потрібна таблиця. Але він усе одно проходить 554 тис. записів індексу й агрегує їх, а таблиця і так лежала в пам'яті, тож Seq Scan і без того був швидким. На диску з холодним кешем виграш був би більшим: Seq Scan читав би 432 МБ, а Index Only Scan — лише потрібний відрізок індексу.

## Завдання 4. Рівні ізоляції: одночасне оновлення бронювання

Сценарій перевірено на двох паралельних сесіях psql (бронювання `id = 42`). Оператор (A) читає бронювання двічі з паузою 2 с; між читаннями шлюз (B) виконує `UPDATE bookings SET status = 'checked_in' WHERE id = 42` з автоматичним `COMMIT`. Виводи — у `results/isolation_*.txt`.

| Рівень оператора | 1-ше читання | 2-ге читання | `UPDATE` оператора |
|---|---|---|---|
| Read Committed | `paid` | **`checked_in`** | — |
| Repeatable Read | `paid` | `paid` | `ERROR: could not serialize access due to concurrent update` |
| Serializable | `paid` | `paid` | `ERROR: could not serialize access due to concurrent update` |

**1. Аномалія на Read Committed** — **non-repeatable read** (неповторюване читання). На Read Committed кожен `SELECT` бачить знімок даних на момент **свого** початку, тому друге читання бачить зміну, яку B вже закомітив. Так, оператор бачить **різні значення** `status`: `paid`, потім `checked_in` (див. [results/isolation_read_committed.txt](results/isolation_read_committed.txt)). Dirty read тут неможливий: PostgreSQL ніколи не показує незакомічені дані, навіть на Read Uncommitted.

**2. Потрібний рівень — Repeatable Read** (`BEGIN ISOLATION LEVEL REPEATABLE READ`). Він гарантує, що вся транзакція бачить **один знімок** на момент першого запиту: повторне читання того самого рядка дає те саме значення, а чужі коміти, зроблені після початку транзакції, невидимі. У PostgreSQL цей рівень також не допускає phantom read. А якщо оператор спробує змінити рядок, який уже змінила інша транзакція, PostgreSQL не дасть «перезаписати наосліп» і поверне помилку (`could not serialize access due to concurrent update`). Так оператор не зробить повернення коштів на основі застарілих даних.

**3. Побічний ефект Serializable.** Serializable гарантує, що результат буде таким, ніби транзакції виконувалися **по черзі**. Для цього PostgreSQL відстежує залежності читання/запису між транзакціями (SSI) і обриває транзакцію з помилкою `40001 serialization_failure` не лише при конкурентному `UPDATE` того самого рядка, а й при будь-якому «небезпечному» поєднанні читань і записів, навіть коли рядки різні. Для коду застосунку це означає:
- **обов'язкова логіка повтору (retry)**: перехопити `SQLSTATE 40001` і повторити всю транзакцію спочатку;
- такі помилки трапляються **частіше**, ніж на Repeatable Read, особливо під навантаженням;
- додаткові накладні витрати на відстеження предикатних блокувань.

Для сценарію оператора достатньо Repeatable Read: він закриває non-repeatable read, а повтор потрібен лише у випадку реального конфлікту на тому самому рядку.

## 1. RED — тест на межове значення

```python
def test_discount_at_threshold_is_applied():
    calc = LoyaltyDiscountCalculator()
    assert calc.calculate(1000) == 100
```

Тест виражає специфікацію («від 1000 включно»), а не поточну поведінку. Результат на старому коді (`results/red_output.txt`):

```
tests/test_discount.py ..F                                               [100%]

>       assert calc.calculate(1000) == 100
E       assert 0.0 == 100
E        +  where 0.0 = calculate(1000)

FAILED tests/test_discount.py::test_discount_at_threshold_is_applied - assert...
========================= 1 failed, 2 passed in 0.11s ==========================
```

**Чому падає:** для `booking_total = 1000` умова `1000 > 1000` хибна, тому код іде в гілку «без знижки» і повертає `0.0`; при `>=` умова була б істинною.

Старі тести (500 і 2000) зелені, бо жоден не перевіряє саму межу.

## 2. GREEN — мінімальне виправлення

Змінено рівно одну умову:

```diff
     def calculate(self, booking_total: float) -> float:
         """Повертає суму знижки для бронювання на суму booking_total."""
-        if booking_total > self.DISCOUNT_THRESHOLD:
+        if booking_total >= self.DISCOUNT_THRESHOLD:
             return booking_total * self.DISCOUNT_RATE
         return 0.0
```

Після правки весь набір зелений: `3 passed` (`results/green_output.txt`). RED-тест залишено як регресійний.

## 3. Property-based тест — інваріант

Генератор: `st.floats(min_value=0, max_value=100_000, allow_nan=False, allow_infinity=False)` — будь-які суми, зокрема дробові.

**Інваріант (б), основний:**
> для будь-якої суми `total` від 0 до 100 000 знижка дорівнює рівно `total * 0.10`, якщо `total >= 1000`, і рівно `0.0`, якщо `total < 1000`.

**Інваріант (а), додатковий:** знижка ніколи не від'ємна і ніколи не більша за 10% суми.

**Чому обрано (б):** він повністю описує специфікацію з обох боків від межі, тому ловить саме той клас помилок, що був у коді (неправильна межа), а не лише «щось розумне».

Інваріант (в) про монотонність тут **не підходить**: ціна після знижки не монотонна (999 грн → 999, а 1000 грн → 900). Це очікувана поведінка за специфікацією, а не баг.

Важливе спостереження: випадкові float майже ніколи не дають рівно `1000.0`. Я перевірив: якщо повернути `>`, тест лише з `@given` пройшов зеленим. Тому межові точки додано явно через `@example(total=1000.0)` і `@example(total=999.99)`. Генератор при цьому працює як завжди (`max_examples=500`). Тепер на старому коді тест падає:

```
E           Failing explicit example: test_property_discount_matches_specification(
E               total=1000.0,
E           )
```

Після виправлення hypothesis контрприкладів не знаходить: `5 passed` (`results/property_output.txt`).

## 4. Мутаційне тестування

Інструмент: **mutmut 2.5.1** (`setup.cfg`). Він мутує і тіло методу, і константи класу — разом 7 мутантів (`results/mutants_list.txt`).

| # | Мутація | Що моделює | Хто вбиває (повний набір) |
|---|---|---|---|
| 1 | `DISCOUNT_THRESHOLD = 1000` → `1001` | поріг зсунуто на одиницю | RED-тест, property `@example(1000.0)` |
| 2 | `DISCOUNT_THRESHOLD = 1000` → `None` | поріг не задано | усі тести (TypeError) |
| 3 | `DISCOUNT_RATE = 0.10` → `1.1` | неправильний відсоток | `test_discount_above_threshold`, property |
| 4 | `DISCOUNT_RATE = 0.10` → `None` | відсоток не задано | `test_discount_above_threshold` (TypeError) |
| 5 | `>=` → `>` | **той самий баг**, що був у коді | RED-тест, property `@example(1000.0)` |
| 6 | `*` → `/` | ділення замість множення | `test_discount_above_threshold`, property |
| 7 | `return 0.0` → `return 1.0` | знижка нижче порогу ≠ 0 | `test_no_discount_below_threshold`, property |

Підсумок:

| Набір тестів | Мутантів | Вбито | Вижило | Mutation score |
|---|---|---|---|---|
| Лише 2 старі тести (для порівняння) | 7 | 5 | 2 (#1, #5) | **71%** |
| Повний набір: 2 старі + RED + 2 property — початковий прогін | 7 | 7 | 0 | **100%** |
| Після дописаних тестів | — | — | — | дописувати не знадобилося |

- Старі тести мали 100% покриття рядків, але пропускали обидва «межові» мутанти. Це саме те, чим мутаційне тестування краще за покриття: рядок виконується, але результат на межі ніхто не перевіряє.
- Обидва мутанти, що виживали, моделюють зсув межі, і їх вбиває RED-тест. Тому з повним набором вижилих мутантів немає. Додаткові тести не потрібні, поріг 80% виконано.
- Виводи: `results/mutmut_baseline_old_tests.txt`, `results/mutmut_full_suite.txt`.
- Додатково перевірив mutmut 3.8: він мутує лише тіла функцій, тому знайшов 3 мутанти (#5, #6, #7) — усі вбиті, 100%.

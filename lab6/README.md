## Завдання 1. Вибір типу бази через CAP

| Підсистема | Вибір | CAP |
|---|---|---|
| Бронювання номерів | **реляційна БД** (PostgreSQL) | **CP** |
| Стрічка «що бронювали ваші друзі» | **Wide-Column** (Cassandra / ScyllaDB) | **AP** |
| Граф рекомендацій готелів | **Graph** (Neo4j) | **AP** для читання |

### 1. Бронювання номерів — реляційна БД, CP

**CAP.** Правило «один номер на одні дати — лише одному гостю» не можна порушити навіть на секунду. Подвійне бронювання означає, що один гість приїде і не матиме де ночувати. Тому потрібна сувора консистентність, навіть ціною тимчасової відмови: краще сказати «спробуйте за хвилину», ніж продати номер двічі.

**Split-brain.** Мережа розірвалась, кластер розпався на дві частини. Гість A бронює номер 305 на 1–3 грудня через вузол у частині 1, гість B — той самий номер через вузол у частині 2.
- У CP-системі запис приймає лише частина з більшістю (або лише primary). Частина без більшості відповідає помилкою.
- Гість B бачить «сервіс тимчасово недоступний», але номер не продано двічі.
- Після відновлення мережі B бачить, що номер уже зайнятий.

**Патерн доступу.** Бронювання — це транзакція: перевірити, що номер вільний, і записати бронь атомарно. PostgreSQL робить це на рівні схеми:

```sql
CREATE EXTENSION btree_gist;
ALTER TABLE bookings ADD CONSTRAINT no_double_booking
    EXCLUDE USING gist (room_id WITH =, daterange(check_in, check_out) WITH &&);
```

Обмеження `EXCLUDE` гарантує, що два бронювання одного номера не перетинаються за датами, навіть при паралельних запитах. Плюс ACID-транзакції, зв'язки «готель — номер — гість — оплата» і звіти (як у Лабораторній №5). Обсяг даних помірний (тисячі бронювань на день), тож горизонтальне масштабування NoSQL тут не потрібне.

### 2. Стрічка «що бронювали ваші друзі» — Wide-Column, AP

**CAP.** Якщо бронювання друга з'явиться у стрічці на хвилину пізніше або двоє користувачів на мить побачать різний порядок записів — нічого поганого не станеться. Важливіше, щоб стрічка завжди відкривалась у мільйонів користувачів. Тому AP: доступність і масштаб ціною тимчасової неконсистентності (eventual consistency).

**Split-brain.** Кластер розпався на дві частини (наприклад, два дата-центри).
- Обидві частини далі приймають запити: стрічка відкривається у всіх.
- Друг забронював готель, запис потрапив у частину 1. Користувач, якого обслуговує частина 2, поки не бачить цього запису.
- Після відновлення мережі репліки синхронізуються (hinted handoff, read repair), і запис з'являється. Конфлікти вирішує last-write-wins, а для стрічки це нормально.

**Патерн доступу.** Стрічка — це «дай 20 останніх записів для user_id». У Wide-Column таблиця будується саме під цей запит:

```
feed_by_user (
    user_id      PARTITION KEY,       -- уся стрічка користувача на одному вузлі
    created_at   CLUSTERING KEY DESC, -- записи вже відсортовані за часом
    friend_id, hotel_id, hotel_name, city
)
```

- Читання — один послідовний відрізок однієї партиції, без JOIN.
- Запис дешевий (append-only, LSM-дерево). Бронювання друга копіюється у стрічки його друзів (fan-out on write).
- Старі записи видаляються автоматично через TTL (`USING TTL 604800` — тиждень).
- Масштабується додаванням вузлів.

### 3. Граф рекомендацій готелів — Graph, AP для читання

**CAP.** Рекомендації — це підказка. Якщо вони на кілька хвилин застаріли (не врахували бронювання, зроблене щойно), користувач цього не помітить. Тому для читання прийнятний AP: рекомендації читаються з read-реплік, що можуть трохи відставати.

**Split-brain.** Частина реплік відрізана від основного кластера.
- Відрізані репліки далі віддають рекомендації — трохи застарілі, без нових ребер.
- Нові ребра «користувач забронював готель» тимчасово не записуються (у Neo4j записи йдуть через лідера Raft) і потрапляють у граф із черги після відновлення.
- Користувач бачить рекомендації, просто без найсвіжіших даних.

**Патерн доступу.** «Гості, що бронювали цей готель, також бронювали…» — це обхід графу на 2–3 кроки:

```cypher
MATCH (h:Hotel {id: $hotel})<-[:BOOKED]-(u:User)-[:BOOKED]->(other:Hotel)
WHERE other <> h
RETURN other, count(u) AS score ORDER BY score DESC LIMIT 10
```

- У графовій БД кожен вузол зберігає прямі посилання на сусідів (index-free adjacency), тому обхід коштує пропорційно кількості пройдених ребер, а не розміру всіх таблиць.
- У реляційній БД той самий запит — це кілька self-JOIN великої таблиці бронювань, і з кожним кроком він дорожчає.

## Завдання 2. Cache-aside

`hotel_cache/cached_service.py`:

```python
def get_room(self, room_id: str) -> dict:
    cached = self._cache.get(room_id)
    if cached is not None:               # cache hit -- у базу не йдемо
        self.hits += 1
        return cached
    self.misses += 1                     # cache miss
    room = self._backend.get_room(room_id)
    if room is not None:
        self._cache.set(room_id, room)
    return room
```

- **Cache hit** — дані повертаються з кешу, `SlowRoomAvailabilityService` не викликається взагалі.
- **Cache miss** — виклик бази, запис у кеш з TTL, і лише потім повернення результату.
- **TTL** — `TtlCache` зберігає для кожного ключа час закінчення (`time.monotonic() + ttl`). Прострочений запис видаляється при читанні і вважається промахом.
- `None` (номер не існує) не кешується.
- `invalidate(room_id)` — активна інвалідація для Завдання 4.
- `SlowRoomAvailabilityService` не змінювався: увесь код кешування — у новому класі-обгортці.

Тести (`python test_cache.py`) перевіряють: другий запит не йде в базу, запис живе рівно TTL (годинник підмінено), застаріла ціна до інвалідації, `None` не кешується, LRU-витіснення.

## Завдання 3. Вимірювання ефекту

`benchmark.py`: 500 запитів, `random.Random(42)`. 80 % запитів — на 10 «гарячих» номерів (`room-1` … `room-10`), 20 % — рівномірно на решту 40. Та сама послідовність проганяється двічі. TTL = 30 с, увесь прогін через кеш триває ~7 с, тож записи не встигають прострочитись.

Результат (`results/benchmark.txt`):

```
Запитів: 500, унікальних номерів у послідовності: 48
Варіант                           Час, с   Сер. затримка, мс  db_calls
SlowRoomAvailabilityService        75.08              150.16       500
CachedRoomAvailabilityService       7.21               14.42        48
Cache hits: 452, misses: 48, hit ratio: 90.4%
Прискорення: x10.4, навантаження на БД менше в x10.4
```

- **Час відповіді** зменшився в **10,4 раза**: 150 мс → 14,4 мс у середньому на запит.
- **Навантаження на базу** зменшилось у **10,4 раза**: 500 → 48 звернень. Кожен із 48 різних номерів, що трапились у послідовності, читався з бази рівно один раз.
- Hit ratio 90,4 %. Майже весь час кешованого варіанта — це 48 промахів по 150 мс. Cache hit займає мікросекунди.
- Що довша послідовність, то більший виграш: кількість промахів обмежена кількістю номерів, а не кількістю запитів.

## Завдання 4. TTL, eviction та інвалідація

### TTL = 30 секунд

Компроміс **staleness проти correctness**:
- Дані номера — ціна і прапорець «вільний» — змінюються, коли номер бронюють або коли менеджер змінює ціну. Це відбувається рідко порівняно з кількістю переглядів: гарячий номер у сезон переглядають десятки разів на секунду.
- 30 с — це коротке вікно застарілості: гість максимум пів хвилини може бачити номер вільним після того, як його забронювали.
- Водночас для гарячого номера, який переглядають 10 разів на секунду, 30 с дають ~300 попадань на один похід у базу. Це знімає основне навантаження «Чорної п'ятниці».
- **Correctness забезпечує не кеш.** Кеш використовується лише для показу каталогу. Фінальне бронювання завжди йде в реляційну CP-базу з обмеженням `EXCLUDE` (Завдання 1). Якщо кеш показав «вільний», а номер уже зайнятий, бронювання не пройде і гість отримає повідомлення.
- Довший TTL (години) дав би помітно більше скарг «показали вільним, а забронювати не можна». Коротший (1–2 с) майже не розвантажив би базу.

### Eviction policy — LRU

Якщо пам'яті не вистачає, я обрав би **LRU** (Least Recently Used). Саме LRU реалізовано в `TtlCache`, в Redis це `maxmemory-policy allkeys-lru`.
- Популярність готелів **швидко змінюється**: дати заїзду наближаються і минають, починаються розпродажі, сезон змінюється. LRU одразу підлаштовується: що шукають зараз, те й у кеші.
- **LFU** накопичує лічильники за весь час. Номери, що були популярні минулого тижня (наприклад, на святкові дати, які вже минули), довго займали б пам'ять через великий лічильник.
- Ризик LRU — разове сканування «холодних» номерів (наприклад, бот-краулер) може витіснити гарячі. Це пом'якшує TTL і обмеження частоти запитів для ботів. Також можна взяти `allkeys-lfu` у Redis, де лічильники з часом згасають (decay).

### Ситуація із застарілою ціною

1. О 10:00:00 гість відкриває номер `room-3`. Cache miss → у кеш записано ціну 1030 грн, запис живе до 10:00:30.
2. О 10:00:05 менеджер в адмінпанелі змінює ціну на 1500 грн. База оновилась, кеш — ні.
3. До 10:00:30 усі гості бачать стару ціну 1030 грн. Хтось починає бронювання за ціною, якої вже немає.

Це відтворює тест `test_stale_price_until_invalidation`.

**Як пом'якшити:**
- **Активна інвалідація.** Після успішного `UPDATE` ціни адмінпанель викликає `invalidate(room_id)` (у Redis — `DEL room:room-3`). Наступний запит — cache miss, і гість бачить нову ціну. Те саме робить сервіс бронювання після запису бронювання (номер став зайнятим).
- Якщо сервісів багато, адмінпанель публікує подію `RoomPriceChanged`, а кожен екземпляр кешу на неї підписаний.
- **Остаточна ціна — з бази.** На кроці оплати ціна читається з реляційної бази, а не з кешу. Тоді навіть пропущена інвалідація не призведе до оплати за неправильною ціною.
- TTL залишається запобіжником: якщо подію інвалідації втрачено, запис усе одно прострочиться через 30 с.

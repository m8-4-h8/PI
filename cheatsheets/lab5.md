# Лаба 5 — индексы, EXPLAIN ANALYZE, уровни изоляции. Шпаргалка

Вариант 1: таблица `bookings` (5 млн бронирований отелей). Отчёт: топ-20 отелей по сумме оплаченных броней за 2026 год.
Всё уже сделано и измерено: [lab5/README.md](../lab5/README.md), полные выводы в `lab5/results/`.

## Главные цифры (выучить)

| | План | Время |
|---|---|---|
| без индекса | Parallel Seq Scan | 220 мс |
| индекс `(status, created_at)` | Bitmap Heap Scan | 310 мс (медленнее!) |
| покрывающий индекс `+ INCLUDE (hotel_id, total)` | Index Only Scan | 112 мс (в 2 раза быстрее) |

- Таблица: 55 355 страниц по 8 КБ = 432 МБ.
- Под условие попадают 554 668 строк = 11 % таблицы.
- INSERT с индексом примерно в 2 раза медленнее (1091 мс против 526 мс на 200 тыс. строк).

## Суть через аналогии

**Seq Scan — читать всю книгу подряд.** Нужно найти все страницы про «оплаченные брони 2026 года». Без оглавления листаешь все 55 тыс. страниц. Время зависит от толщины книги, а не от того, сколько нужно найти.

**B-Tree индекс — алфавитный указатель в конце книги.** Записи отсортированы, поэтому можно найти и точное слово (`status = 'paid'`), и диапазон (`created_at >= 2026-01-01`).
**Hash — гардероб с номерками.** По номерку мгновенно находишь пальто, но спросить «все пальто с номерами от 100 до 200» нельзя. Поэтому Hash не подходит для диапазона дат.

**Порядок столбцов `(status, created_at)` — телефонная книга «Фамилия, Имя».** Легко найти всех «Ивановых» с именами от А до К: они идут подряд. Если бы книга была отсортирована по имени, Ивановы были бы разбросаны. Правило: сначала столбцы с `=`, в конце столбец с диапазоном.

**Почему первый индекс не помог — нужные строки на каждой странице.** Указатель говорит: «нужное есть на страницах 1, 2, 3, … 55 355». На каждой странице ~10 нужных строк из ~90. Всё равно читаешь всю книгу, да ещё и сначала тратишь время на указатель.

**Покрывающий индекс — шпаргалка, где уже есть ответ.** В указатель дописали ещё `hotel_id` и `total`. Теперь в саму книгу (таблицу) ходить не нужно: `Heap Fetches: 0`.

**Цена индекса — каждую новую страницу надо внести и в указатель.** Поэтому INSERT медленнее. Для броней это нормально: бронь добавляется по одной, пару микросекунд никто не заметит.

## Уровни изоляции через аналогию

Оператор смотрит бронь, готовит возврат денег и через пару секунд проверяет ещё раз. В это время платёжный шлюз меняет статус `paid` → `checked_in`.

- **Read Committed — смотришь в окно.** Каждый взгляд показывает то, что сейчас. Первый раз `paid`, второй раз `checked_in`. Это **non-repeatable read**.
- **Repeatable Read — сделал фото в начале.** Всю транзакцию смотришь на одно и то же фото: оба раза `paid`. Если попробуешь изменить бронь, которую уже поменяли, получишь ошибку `could not serialize access`. Так возврат не сделается по устаревшим данным.
- **Serializable — как будто все стоят в одной очереди.** Самый строгий уровень. Ошибки `40001` бывают чаще, даже при разных строках, поэтому в коде обязательно нужен **повтор (retry)** транзакции.

Термины: **dirty read** — видеть чужие незакоммиченные данные (в PostgreSQL невозможно). **Non-repeatable read** — та же строка при повторном чтении другая. **Phantom read** — повторный запрос с условием вернул новые строки.

## Вопросы к защите

1. **Почему без индекса запрос медленный?**
   Seq Scan читает все 55 355 страниц таблицы (432 МБ), хотя нужны только 11 % строк. 89 % прочитанного отбрасывается фильтром.
2. **Почему B-Tree, а не Hash, и почему такой порядок столбцов?**
   В запросе есть диапазон `created_at >= ...`, а Hash умеет только равенство. Сначала `status` (равенство), потом `created_at` (диапазон): тогда нужные записи лежат одним отрезком.
3. **Почему первый индекс сделал запрос медленнее?**
   Нужные строки разбросаны по всем страницам, поэтому Bitmap Heap Scan всё равно прочитал всю таблицу, плюс время на индекс. Помог покрывающий индекс: Index Only Scan без обращения к таблице, 220 → 112 мс.
4. **Что такое cost в плане?**
   Условные единицы планировщика, а не миллисекунды. Время — только в `actual time` и `Execution Time`.
5. **Какая аномалия на Read Committed и что выбрать?**
   Non-repeatable read: оператор видит `paid`, потом `checked_in`. Нужен Repeatable Read. Минус Serializable — частые ошибки сериализации, нужен retry.

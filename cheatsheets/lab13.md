# Лаба 13 — System Design: real-time мессенджер. Шпаргалка

Вариант 1 → выбрана система **A — мессенджер** (аналог WhatsApp / Telegram). Данные базовые: 50 млн зарегистрированных, 5 млн DAU, 40 сообщений на пользователя в день.

## Главные цифры (выучить)

- **Сообщения:** 5 млн × 40 = 200 млн/день → **2 315 msg/s** в среднем, **6 944** в пик (×3), **23 148** в Новый год (×10).
- **Доставки:** 0,7 × 1 + 0,3 × 9 = **3,4** на сообщение → 23 611/с в пик, 78 704/с в Новый год.
- **WebSocket:** 5 млн × 2,5 ч / 24 = 520 833 онлайн → ×2 в пик = 1,04 млн (20,8% DAU) → ×1,3 устройства = **1,35 млн соединений**. 50 000 на узел → 27 → с запасом на зону **41 узел**. Heartbeat — **45 000/с** (больше, чем сообщений!).
- **Хранилище за 2 года:** 146 млрд сообщений × 200 Б = **29,2 ТБ** → ×3 реплики = 87,6 → +30% compaction = **114 ТБ** (29 узлов по 4 ТБ). Медиа отдельно — **4,4 ПБ** в object storage.
- **Presence наивно:** 50 переходов × 30 онлайн-контактов = 1 500 событий на человека в день → **86 806/с**, в **37 раз больше**, чем сообщений. Оптимизированно — 16 × 3 = 48 → **2 778/с** (в 31 раз меньше).
- **Модели:**
  - Dedup: без дедупликации было бы 25 125 строк вместо 20 000 (каждое пятое — дубль). С дедупликацией — ровно 20 000, у всех участников 1..N без повторов.
  - Presence, обычный час: 3,6 млн → 66 тыс. событий (**×54**).
  - Presence, сбой зоны (508 соединений): **36 739 → 78** событий; 476 из 508 вернулись в grace без единого события.

## Суть решения одним абзацем

Главное требование — **N1: ни одно сообщение с «одной галочкой» не теряется, дублей не видно, порядок одинаков везде**. Поэтому:
- **сначала запись, потом ACK:** «отправлено» только после записи кворумом в Message Store (Cassandra);
- **at-least-once везде + дедупликация по `message_id` на трёх уровнях;**
- **порядок по `server_seq`** внутри разговора;
- **доставку запускает CDC из Message Store в Kafka** (партиция = `conversation_id`), а не код сервиса — нет проблемы dual write из лабы 7;
- **офлайн-получатель:** Undelivered Queue + Push Service + sync по курсору `last_seq`.

## Компоненты (имена как на схеме)

- **Соединения:** L4 Load Balancer (Least Connections) → **Connection Gateway** (WebSocket, stateful) ↔ **Session Registry** (Redis: пользователь → узел).
- **Запись:** **Message Service** (stateless) → **Dedup Cache + Sequence** (Redis) → **Message Store** (Cassandra: `messages ((conv, month), seq)` и `msg_by_client_id`).
- **Доставка:** Message Store → CDC → **Kafka** → **Delivery Workers** → онлайн: Connection Gateway; офлайн: **Undelivered Queue** + **Push Service** → APNs / FCM.
- **Presence:** **Presence Service** + Presence Store (Redis).
- **Прочее:** API Gateway → Sync API, Media Service → Object Storage + CDN; Group Service.

## Аналогии

- **`message_id` — номер квитанции, которую ты сам выписал до отправки.** Отправил письмо дважды — на почте видят тот же номер и второе не регистрируют.
- **`server_seq` — номер страницы в общем дневнике разговора.** Если после страницы 5 пришла 7-я — значит, 6-я потерялась, надо попросить (sync).
- **Три уровня дедупликации — три охранника:** отправитель не придумывает новый номер при повторе, сервер не пишет второй раз, получатель не показывает дважды.
- **Наивный presence — громкоговоритель:** «Максим вышел!» на весь подъезд каждый раз, когда ты выходишь за хлебом на 20 секунд.
- **Оптимизированный presence — табличка на двери:** её видят только те, кто сейчас смотрит на твою дверь, и меняют не раньше чем через 30 секунд.
- **Шторм переподключений — все разом ломятся в одну дверь после отключения света.** Jitter — людей пускают с разбросом во времени.

## Вопросы к защите

1. **Почему главное требование — надёжность доставки, а не латентность?**
   Задержку 0,5 с никто не заметит, а потерянное или задвоенное сообщение рушит доверие. N1 определяет архитектуру: запись перед ACK, at-least-once + дедупликация, `server_seq`, CDC вместо dual write, очередь недоставленных. Латентность (N2) требует WebSocket и Connection Gateway, но имеет смысл только поверх N1.
2. **Как устроен `message_id` и где проверяется?**
   128 бит = `device_id` (64, выдаёт сервер) + `client_seq` (64, счётчик в локальной SQLite). Создаётся **до** первой попытки и не меняется при повторах. Проверка на трёх уровнях:
   - outbox отправителя — повтор идёт с тем же id;
   - Message Service — Redis `SET NX` с TTL 24 ч, а для повторов (`attempt > 1`) ещё и таблица `msg_by_client_id` в Cassandra;
   - получатель — `UNIQUE(message_id)` в локальной БД.
   Время в id не кладём, потому что часы телефонов врут.
3. **Что будет, если сервер упал после записи, но до ACK, и ещё Redis потерял ключи?**
   Клиент повторит с `attempt = 2`. В Redis ключа нет, поэтому сервер ищет в `msg_by_client_id`, находит и возвращает тот же `seq`. Доставка не потерялась: её запустил CDC от самой записи.
4. **Зачем `pending` с lease 10 с?**
   Если два запроса с одним id пришли одновременно, второй получит «in progress». Если инстанс упал после захвата, через 10 с другой перехватит обработку.
5. **Как Presence Service ограничивает fan-out при массовой смене статусов?**
   - подписка только на тех, кто на экране (≤ 20);
   - grace 30 с (фон) / 60 с (обрыв): переподключение внутри grace — ноль событий, last seen = момент отключения;
   - coalescing за 2 с, остаётся только последнее состояние;
   - heartbeat не идёт в Presence;
   - в группах > 100 — только счётчик «N онлайн»;
   - режим «шторм» с grace 120 с и низким приоритетом.
   Модель: сбой зоны — 36 739 событий наивно против 78.
6. **Назови конкретные узкие места.**
   - **Шторм переподключений:** 50 000 клиентов в одну секунду → каскад по соседним узлам. Решение — jitter, graceful drain, bulkhead (лаба 10).
   - **Горячая большая группа:** одна партиция Kafka → head-of-line blocking для чужих чатов. Решение — fan-out on read, отдельный топик, алерт на lag.
   - **Push в Новый год:** ~47 000/с, APNs отвечает 429. Решение — collapse key, отдельный топик, CB + bulkhead; push — только подсказка.
   - **Session Registry:** до 78 700 lookup/с. Решение — Redis Cluster, MGET, локальный кеш.
7. **Почему Cassandra, а не PostgreSQL?**
   - нагрузка — в основном запись (до 23 000/с × 3 реплики);
   - доступ всегда «разговор по порядку seq» — ложится на wide-column;
   - 114 ТБ масштабируются горизонтально;
   - месячный bucket в ключе партиции не даёт партиции расти бесконечно.

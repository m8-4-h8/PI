# Лаба 14 — RAG для базы знаний поддержки. Шпаргалка

Вариант 1 = **PeopleFlow** (B2B SaaS для кадров и зарплат). Цифры из легенды: 200 клиентов, 3 000 обращений в неделю, ≥ 60% повторяются.
База знаний:
- 340 статей;
- 85 страниц API расчёта зарплат с кодами ошибок `ERR_4092`;
- 12 000 тикетов;
- вики кадровой и бухгалтерской политики (обновляется раз в месяц).

## Главные цифры (выучить)

- **Фрагментов после chunking ≈ 5 000:**
  - статьи — 945 (170 000 слов / 180);
  - API — 561 (221 endpoint + 340 кодов ошибок);
  - тикеты — 3 360 (12 000 × 0,4 после дедупа × 0,7 без мусора);
  - политики — 134.
  - Без дедупа тикетов было бы 13 640.
- **Память:** 1024 × 4 Б = 4 КБ на вектор → 5 000 × 4 КБ × 1,5 HNSW ≈ **29 МБ**.
- **Нагрузка:** 3 000 × 2,5 = 7 500 вопросов в неделю / 50 ч = 150 в час = **0,04 QPS**. Пик (дни выплат + утро понедельника) ≈ 2 QPS, закладываем **5 QPS**.
- **Промпт ≤ 8 000 токенов:** инструкция ~150, клиент ~50, история ≤ 1 500 (сводка + 3 последние реплики), фрагменты ~5 000, вопрос ~200, резерв на ответ 800.
- **Порог уверенности 0,35** (скор cross-encoder): ниже — эскалация без вызова LLM.
- **Демо chunking:** fixed-size 400 символов — **6 из 6** фрагментов битые; структурный — 7 фрагментов, **0** битых.
- **Демо поиска (только BM25):** точные коды — Hit@5 100%, MRR 0,90; перефразированные — **Hit@5 60%, MRR 0,40**. Это и есть аргумент за гибрид.

## Суть решения одним абзацем

- **Chunking:** свой для каждого типа контента, фрагмент никогда не рвёт таблицу, шаги или код, у каждого есть заголовок-контекст.
- **Хранилище:** pgvector в уже существующем PostgreSQL. Объём крошечный, нужна транзакционность (замена редакции политики, удаление данных клиента), а sparse-поиск (tsvector) живёт там же.
- **Поиск:** гибрид dense + BM25 через RRF, точный код ошибки закрепляется, затем cross-encoder top-20 → top-5.
- **Порог и промпт:** порог уверенности, промпт с бюджетом, проверка ссылок `[n]`, эскалация с полным контекстом.
- **Архитектура:** порты и адаптеры — LLM-провайдер меняется одним адаптером.

## Chunking по типам

| Тип | Как режем | Почему |
|---|---|---|
| Статьи | по `##`, нумерованный список целиком, название статьи в начале | ответ = полная последовательность шагов |
| API | endpoint целиком (описание + вся таблица + пример); длинную таблицу режем по группам строк **с повтором шапки и endpoint**; **каждый код ошибки — отдельный фрагмент** | строка таблицы без шапки и endpoint — набор слов; коды ищут точно |
| Тикеты | пара «вопрос — финальный ответ», **обезличивание** (РНОКПП, IBAN, телефон, email, имена), слияние дублей, доверие ×0,8 | PII другого клиента в ответе — утечка; дубли забивают top-5 |
| Политики | по пунктам, с **датой редакции**; обновление страницы — замена всех фрагментов в одной транзакции | нельзя смешать старую и новую редакцию |

**Чем опасен fixed-size для таблицы параметров:**
- строки без шапки — модель не знает, что «так» значит «обязательный»;
- строки без endpoint — POST или GET?;
- строка `ERR_4221` (ошибка POST) попала под заголовок GET;
- строка кода ошибки разрезана пополам;
- перекрытие 50 символов — это полстроки, оно не спасает.

## Аналогии

- **Fixed-size chunking — разрезать таблицу умножения ножницами каждые 10 см.** В одном куске «7 × 8 =», в другом «56».
- **Dense vs sparse — библиотекарь, который понимает смысл, и поиск по каталогу.** Библиотекарь найдёт «книгу про то, как не платить налоги дважды», но перепутает ERR_4091 и ERR_4092. Каталог найдёт ровно ERR_4092, но не поймёт перефразировку. Гибрид — спросить обоих и объединить списки (RRF).
- **Cross-encoder — второе собеседование.** Первый отбор по резюме быстрый (bi-encoder), на второе зовут 20 кандидатов и смотрят внимательно, вопрос рядом с ответом.
- **Порог уверенности — врач, который не уверен в диагнозе и направляет к специалисту,** а не выписывает рецепт наугад.
- **Hexagonal — розетка и вилка.** Поменять LLM-провайдера = поменять вилку, проводка в стене (use case) та же.

## Вопросы к защите

1. **Почему разные стратегии chunking, а не одна?**
   У четырёх источников разная структура и разный способ поиска:
   - статьи — шаги, нужна вся последовательность;
   - API — таблицы и точные коды;
   - тикеты — уже готовые пары Q&A с PII и дублями;
   - политики — пункты с редакциями, которые нельзя смешивать.
2. **Почему pgvector, а не Pinecone/Qdrant? Когда мигрировать?**
   - 5 000 векторов (29 МБ) и 5 QPS — это мизер.
   - Нужна транзакционность: замена редакции политики, удаление данных клиента вместе с тикетами (иначе dual write, лаба 7). Фильтры по tenant — обычный SQL. Полнотекстовый поиск там же. Данные о зарплатах не уходят в чужой SaaS.
   - **Мигрировать**, если: > 10 млн векторов (индексируем документы всех клиентов); > 100–200 QPS (бот для всех ~100 000 сотрудников клиентов); векторный поиск мешает расчёту зарплат в дни выплат. Первый шаг — отдельный инстанс PostgreSQL, потом Qdrant.
3. **Зачем hybrid search, если есть embeddings?**
   - Для embedding-модели `ERR_4092` — несколько subword-токенов, а фрагменты 4091/4092/4093 отличаются одной цифрой, поэтому их векторы почти одинаковы.
   - BM25 видит `ERR_4092` как один редкий токен — точное совпадение.
   - Зато BM25 не понимает перефразировки (в демо Hit@5 60% против 100%).
   - RRF объединяет без калибровки шкал, плюс точный код из вопроса закрепляем принудительно.
4. **Что делаете с длинной историей диалога?**
   - Последние 3 реплики дословно, каждая с лимитом.
   - Старое сжимается в сводку дешёвой моделью, сохраняя факты: коды, endpoint, что уже пробовали.
   - История ≤ 1 500 токенов.
   - Если всё равно не влезает, выкидываем фрагменты с самым низким рангом. Инструкцию и вопрос не трогаем.
   - Демо: 24 реплики → промпт 1 955 токенов.
5. **Когда и как эскалация?**
   - **Триггеры:** тема только для человека (возврат денег, суд, жалоба); скор < 0,35 (LLM даже не вызываем); LLM вернул `INSUFFICIENT_CONTEXT`; нет корректных ссылок `[n]`; клиент нажал «Позвать оператора».
   - **Тикет** содержит вопрос, всю историю, top-5 фрагментов со скорами и черновик бота.
   - **Приоритет high** — для зарплатных тем в дни выплат.
   - **Обратная связь:** одобренный ответ оператора становится новой парой Q&A.
6. **Три метрики и что ловит только каждая.**
   - **Faithfulness (RAGAS, LLM-судья):** модель придумала «компенсацию за отпуск каждый год», которой нет в политике. Поиск верный, пользователь доволен — ловит только она.
   - **Recall@5 / MRR на золотом наборе (без LLM, в CI):** после смены токенизатора на `ERR_4092` приходит `ERR_4093`. Ответ faithful к неверному контексту — ловит только она, и до релиза.
   - **Resolution Rate (без LLM):** статья про е-больничные устарела после изменений ПФУ. Recall = 1 и Faithfulness = 1, но люди через день создают тикеты — ловит только она.
7. **Какая выгода от hexagonal при смене LLM-провайдера?**
   - Меняется только адаптер `LLMPort` (~100 строк) и конфиг. Use case, промпт, пороги, эскалация и тесты не меняются.
   - Можно гонять два адаптера параллельно и сравнить метрики, а откат — это конфиг.
   - Смена embedding-модели тоже локальна, но требует переиндексации (blue/green).

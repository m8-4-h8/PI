# Лаба 8 — Bounded Contexts, карта контекстов, Strangler Fig. Шпаргалка

Вариант 1: монолит отелей **StayHub**, таблицы `rooms` / `bookings`, класс `BookingService`.

## 5 контекстов (выучить)

| Контекст | Что это | Пример колонок |
|---|---|---|
| Catalog | что продаём (маркетинг) | title, description, photos, amenities |
| Booking | кто, когда, за сколько (ядро) | check_in, check_out, status, base_price |
| Payment | деньги | payment_transaction_id, card_last4, refund_status |
| Housekeeping | физическое состояние дверей | floor, cleaning_status, maintenance_note |
| Notifications | сообщить людям | last_notification_sent |

**Слово с разным смыслом — «Room»:** Catalog — тип номера как товар; Booking — свободная ночь в типе номера; Housekeeping — двери 305 на 3 этаже; Payment — понятия нет вообще.

## План миграции

Stage 0 façade + модули → 1 Notifications (CDC) → 2 Housekeeping (CDC в обе стороны) → 3 Payment (Dual Write + сверка) → 4 отчёты (CDC в хранилище). Catalog + Booking остаются модульным монолитом.

## Аналогии

- **Bounded Context — отделы отеля.** У маркетинга, ресепшена, бухгалтерии и горничных свой язык и свои правила. Слово «номер» у каждого своё.
- **Strangler Fig — дерево-душитель.** Новое растёт вокруг старого по веточке, старое отмирает постепенно. Не сносим здание целиком.
- **ACL — переводчик.** Новый сервис не учит «старый язык» монолита (`cleaning_status = 'OOO'`), переводчик превращает его в чистую модель.

## Вопросы к защите

1. **Почему это отдельные контексты, а не просто таблицы?**
   Граница — по языку, инвариантам и причине изменений. Например, Housekeeping меняется из-за работы горничных, его инвариант — «не отдавать номер, пока не проверен», и его единица — конкретные двери, а не тип номера.
2. **Почему Notifications первым?**
   Минимальный риск: только читает, ничего не пишет в чужие данные. Ошибка — опоздавшее письмо. На нём отрабатываем façade, CDC и мониторинг.
3. **Почему для Payment Dual Write, а для отчётов CDC?**
   Для оплаты нельзя лага: администратор сразу после оплаты должен видеть «оплачено», иначе возьмёт деньги ещё раз. Пишет в обе базы только payment-svc, плюс outbox и ночная сверка. Для аналитики лаг в минуты не важен — CDC проще и безопаснее.
4. **Когда выключается мост?**
   После cutover, когда все, кто читал старые колонки, перешли на API или события нового сервиса. Потом колонки read-only на 30 дней и удаление.
5. **Почему не делить Catalog и Booking?**
   Нет доказательств: команды маленькие и работают вместе, нагрузку снимает кэш, релизы идут вместе. Каждый сервис — +1 пайплайн, +1 on-call, +4 точки наблюдаемости. Резка по техническим слоям даст распределённый монолит.

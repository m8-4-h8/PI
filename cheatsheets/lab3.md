# Лаба 3 — Clean Architecture / Ports & Adapters. Шпаргалка

Вариант 1: **HotelBookingService** (бронирование номера в сети отелей).

## Суть в одной фразе

Бизнес-правила не должны знать, **где** хранятся данные и **как** отправляются уведомления. Они говорят «сохрани» и «сообщи», а кто это делает — решают снаружи.

## Аналогия: розетка и вилка

- Ноутбук (бизнес-логика) не знает, откуда ток: от ТЭЦ, солнечной панели или генератора.
- Он знает только **розетку** (порт) — стандартную форму.
- **Адаптер** — это блок питания или переходник, который подключает конкретный источник к этой форме.
- Хотите поменять электростанцию — ноутбук переделывать не нужно.

Так же с базой: `PlaceBookingUseCase` знает только порт `OrderRepositoryPort.save()`. За портом может быть Postgres (`SqlHotelBookingRepository`) или просто список в памяти (`InMemory...` для тестов).

## Аналогия для слоёв: отель

| Слой | В отеле | В коде |
|---|---|---|
| Domain (Entities) | Правила отеля: «нельзя забронировать на 0 ночей», «сумма > 0» | `domain/booking.py`, `is_valid` |
| Use Cases (Application) | Администратор: принял бронь → записал → сообщил гостю | `PlaceBookingUseCase.execute()`, порты |
| Interface Adapters | Журнал, телефон, email — конкретные способы записать и сообщить | `SqlHotelBookingRepository`, `EmailObserver`, `SmsObserver` |
| Frameworks & Drivers | Сама тетрадь, телефонная станция | `psycopg2`, Postgres |

Из исходного кода `place_order`:
- проверка `total > 0` → **Domain**;
- «сохранить, потом уведомить» (порядок шагов) → **Use Case**;
- SQL-запрос `INSERT ...` → **Adapter**;
- `cursor`, `commit`, psycopg2 → **Frameworks & Drivers**;
- вызов Email/Sms Observer → сам вызов через порт в **Use Case**, реализация в **Adapters**.

## Dependency Rule

Стрелки зависимостей смотрят **только внутрь**. Внешний слой знает про внутренний, но не наоборот.
В исходном коде нарушено: бизнес-логика (`OrderService`, внутренний слой) импортирует psycopg2 (самый внешний слой). Из-за этого нельзя протестировать без живой базы и нельзя сменить базу, не правя бизнес-логику.

Аналогия: правила отеля не должны меняться, если отель сменил тетрадь на Excel.

## Что в каком файле (план)

- `domain/booking.py` — класс `HotelBooking` + `is_valid`, комментарий «жодних зовнішніх залежностей».
- `application/ports.py` — `OrderRepositoryPort.save()`, `NotificationPort.notify()`.
- `application/place_booking.py` — `PlaceBookingUseCase(repo, notifiers)`, только порты.
- `adapters/sql_repository.py` — единственное место с SQL и psycopg2.
- `adapters/in_memory_repository.py` — список в памяти.
- `adapters/email_observer.py`, `sms_observer.py` — реализуют `notify`.
- `main.py` — composition root: создаёт конкретные адаптеры и передаёт в use case.
- `test_*.py` — тест use case с InMemory + фейковый notifier, без Postgres.

## Вопросы к защите

1. **Что такое порт и адаптер?**
   Порт — интерфейс, который нужен use case (что сделать). Адаптер — конкретная реализация (как сделать): SQL, память, email.
2. **Какое правило нарушал исходный код?**
   Dependency Rule: бизнес-логика зависела от psycopg2, то есть внутренний слой от внешнего.
3. **Зачем InMemoryOrderRepository?**
   Чтобы тестировать use case быстро и без базы. Use case не меняем — подставляем другой адаптер.
4. **Что такое composition root?**
   Одно место (`main.py`), где собираются конкретные объекты и передаются через конструктор. Только там код знает про SQL-адаптер.
